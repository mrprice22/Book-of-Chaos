# v0.2 Scope — "Earned Completion"

**Status: authoritative scope contract for the autopilot.** Approved 2026-08-07,
superseding [mvp-scope.md](./mvp-scope.md), which shipped as v0.1 and is now history.
Nothing outside this document gets built before v0.2 is deployed and testable.

v0.1 proved the central thesis: *a dependency graph is a better table of contents than a
list of pages.* It proved it with a gap. Completion is self-reported — a reader clicks
"Mark as complete" and the graph believes them. The prerequisites are therefore
decorative: they gate on an assertion the reader makes about themselves.

v0.2 closes that gap.

> An unlock should be earned, and the server should be the one deciding it was.

---

## The one-sentence v0.2

*An author writes a quiz; a reader cannot pass it by reading the page source, cannot
complete the chapter without passing it, and both of them are doing this at a public URL
rather than on one laptop.*

---

## In scope

### Quiz blocks
- New `BlockType::Quiz` alongside the existing `Reading` and `ResourceLink`
- Question types: **multiple-choice single-answer** and **multiple-choice multi-answer**.
  Nothing else — no free text, no ordering, no matching
- Author-configured pass threshold, as a percentage of questions fully correct
- Grading happens **in a reducer**. The client submits selections and receives a score
- Immediate feedback on submission: score, pass/fail, which questions were wrong
- Unlimited retakes. Retake *policy* (cooldowns, attempt caps, best-vs-last) is deferred
- A `Quiz` block completes only on a passing attempt — never via "Mark as complete"

### The answer key must not reach the browser
This is the load-bearing constraint of the release, and it is an architectural one.
SpacetimeDB pushes table rows to subscribed clients, so a correct-answer column on a
public table is a correct-answer column the reader can read. The intended approach is to
keep the answer key in a **non-public table** that only server-side reducer code can
touch, and to grade in `submit_quiz`.

M10.1 must **verify** this rather than assume it — by attempting to subscribe to the
answer-key table from a real client and asserting the attempt returns nothing. If
SpacetimeDB's table visibility does not work as described, that is a genuine fork in the
road and belongs in `blocked.md`, not a workaround.

### Block-level prerequisites
- A block may declare prerequisite blocks, within its chapter or across chapters
- Validated at **write time**, like chapter deps — reusing `unlock::find_cycle`
- A block with unmet prerequisites cannot be completed, and shows as locked

### Hosted deployment
- The demo runs at a public URL, not only `deploy.sh local`
- Module deployed to a hosted SpacetimeDB instance; client served as a static build
- Host and module name come from build-time configuration — no hardcoded `localhost`

### Debt from v0.1
The three parking-lot entries at the bottom of `docs/backlog.md` are folded in as M9:
the reducer-authorization harness, the deprecated CI actions, and the missing `wasm-opt`.
On approval they are **deleted from the parking lot**, because a thing in two places
drifts in one of them.

## Still deferred

Everything in the v0.1 deferral table stays deferred unless listed above. The additions
this release makes tempting, and their reasons for waiting:

| Deferred | Why it waits |
|---|---|
| `Assignment`, `Reflection`, `Milestone` blocks | `Quiz` is the one that makes unlocking *earned*; the others are submission and meta-block subsystems |
| Peer grading, rubrics, appeals | Needs a reader cohort that does not exist |
| Retake policy: cooldowns, attempt caps, best-vs-last scoring | Each is an author-configuration surface; unlimited retakes prove the loop |
| Partial credit within a question | Scoring model debate for no v0.2 signal |
| Question banks, randomized question order | Same ordering-layer complexity that shuffled blocks was deferred for |
| Block reuse across chapters | Shared completion state is a data-model change; block *prerequisites* do not need it |
| Analytics on quiz results | See "requires readers you do not have yet" |
| Email auth / durable identity | Still needs mail infrastructure; hosting does not change that |

Identity remains anonymous-with-a-localStorage-token. Note the consequence honestly: at a
public URL, a reader who clears their browser loses their progress with no recovery path.
That is a known cost of this release, not an oversight, and it is the strongest candidate
to be v0.3's thesis.

## Definition of Done for v0.2

1. `./scripts/verify.sh` exits 0 from a clean clone, with the `auth-reject` stage included
2. Deleting a `rules::require_owner(...)` call from any author reducer turns the gate red
3. An author can build a quiz through the UI — no SQL, no CLI, no JSON pasting
4. A reader failing a quiz sees their score and stays locked; passing it unlocks the next
   chapter's map node **in a second tab, without reloading**
5. The answer key is provably unreachable from a client subscription (M10.1's test)
6. The demo book is reachable at a public URL by someone who has never cloned the repo
7. CI is green on `main`

Item 5 is the load-bearing one. A quiz whose answers ship to the browser is a "Mark as
complete" button with extra steps — it would leave v0.2 exactly where v0.1 was.
