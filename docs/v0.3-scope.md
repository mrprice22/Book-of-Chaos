# v0.3 Scope — "Branching Works"

**Status: authoritative scope contract for the autopilot.** Approved 2026-10-31, amended
2026-11-19 (see [the amendment](#amendment-2026-11-19)). It takes over from
[v0.2-scope.md](./v0.2-scope.md) **once M13.4, v0.2's last task, closes**. Until then v0.2 is
still being finished, and the backlog's top-to-bottom order already makes that so. Nothing
outside this document gets built before v0.3 is deployed and testable.

v0.1 and v0.2 proved that *a dependency graph is a better table of contents than a list of
pages*, and that the server, not the reader, decides an unlock. Both proofs are about books.

v0.3 makes Book of Chaos a host for **works** of any kind, generated by **integrations** that
live outside this repo. It proves this with a kind that looks nothing like a book: a FATE Core
tabletop game run by the `fate_core_llm` harness (`C:/GIT/fate_core_llm`, its `ROADMAP.yml`
phase P21). A game is a timeline, not a chapter list, and its story branches.

> Every storyline is set in stone. Anyone may go back to any human choice, make a
> different one, and start a branch of their own.

The engine stays out of this repo. Book of Chaos stores, permissions, syncs and renders. An
integration's worker, on its owner's machine, generates the content. **Nothing in this repo
may know what a fate point is.** Fate reaches Book of Chaos the same way any other generator
would: through a contract this repo owns, with its schemas and views carried as data.

---

## The one-sentence v0.3

*A signed-in viewer opens a game at a public URL, scrubs back to a choice the player made
three scenes ago, types a different one, and watches their own private branch play out,
with the character sheet in the side panel showing the state of their branch, while the
original storyline stays exactly as it was. Every panel is drawn by generic blocks from a view
the game registered, and none of it needed a commit to this repo.*

## In scope

### Spikes first (M14)
Five questions decide the design. Each is answered by a test or a recorded run, not by an
opinion, and the answers go in `docs/decisions/`:
- **Owner-only reads.** Can a SpacetimeDB 2.8 view filter a private table by `ctx.sender`,
  so an owner and their authorized worker read rows that no one else can? If not, the
  worker encrypts the owner-only payload before upload, and the server stores it
  without being able to read it.
- **Durable sign-in.** SpacetimeDB's OIDC token support, or a hosted identity provider.
  Whichever is chosen must need no mail server run by this project.
- **Size limits** for a row and for a reducer argument. These bound documents, schemas, view
  manifests and journal payloads.
- **Filtered subscriptions** by `work_id` and `branch_id`, so a client never subscribes to
  every game's every node.
- **A non-browser client:** a Python process calling reducers and SQL over the HTTP API with
  a persistent token. This is the shape of every integration's worker.

### Durable sign-in (M15)
Sign-in survives a cleared browser. An existing `users` row carries its username over.
Anonymous visitors may browse public works but not fork. This absorbs the parking lot's
"durable identity" entry, which is deleted on approval.

### The generic core (M16–M18)
- **`works`:** kind (a string such as `fate`, never an enum the core switches on), owner,
  title, visibility, and `settings_json` (for a game: whether forking is open, caps per user
  and per day).
- **`work_workers`:** the identities an owner authorizes to write on the work's behalf.
- **`work_schemas`:** per work, a `schema_id`, its JSON Schema, and an optional view
  manifest, registered by the owner or an authorized worker. The server checks size and
  ownership, and validates the manifest's shape on write, because every viewer's client
  interprets it. It never validates a document against its schema. That is the
  integration's own gate, and for display, the client's.
- **`nodes`:** an append-only tree. ULID id, work, parent, branch, author identity, role
  (`human` or `worker`), payload. **No reducer updates or deletes a node.** The one
  exception is the owner purging a hidden branch whole.
- **`branches`:** fork node, owner, head, visibility (`private`, `shared` or `public`) and a
  hidden flag. A fork is a new human node whose parent is an existing node's parent.
- **`node_documents`:** typed JSON tagged with a `schema_id` such as `fate.sheet.v1`. A
  document is stored on the node where it changes, and its value at node N is the latest one
  along N's ancestor path. The server checks size and ownership and never reads the body.
- **Owner-only state:** the work's full journal and its checkpoints, in whichever store M14
  chose. It is the cloud backup, and it never reaches a viewer.

### The request queue (M19)
`requests` (fork or turn, branch, text, status, claimed by). Per-user rate limits and the
owner's caps are enforced **in reducers**. A claimed request cannot be claimed twice, and an
abandoned claim times out. The worker's online state is visible, so a waiting request says
why.

### Views and the timeline browser (M20)
- **Generic display blocks:** text, heading, fields (a key-value stat block), list, tags,
  track (a row of boxes, some marked), countdown, and graph (nodes and edges). No block knows
  what kind of work it is drawing.
- **The manifest interpreter.** A document is checked against its registered schema, then
  drawn by its view manifest, which maps the document's fields to blocks and places them in
  a slot. A document with no manifest, or one that fails its schema, renders as a plain,
  read-only JSON view. A manifest's labels are the integration's content, like a book's
  text, so they do not go through `t()`.
- The app shell gains layout slots (main, side panels, composer) that a manifest fills. The
  book screens are unchanged.
- Routes `/w/:workId`, `/w/:workId/b/:branchId` and `/n/:nodeId`.
- A branch tree, a rewind scrubber, and "change this response" on any human node.
- A composer that posts turn requests, since any interactive integration needs one.
- Documents and manifests are JSON and are rendered as text by components. Neither is HTML,
  so `sanitize.rs` is not involved.

### The integration contract (M21)
`docs/contracts/integration/` is owned by this repo and versioned. It holds the protocol
(identity, worker authorization, the reducers and SQL reads a worker uses, the request
lifecycle, the size caps, and one-shot publishing to a work whose forking is off), JSON
Schemas for the document envelope and the view manifest, and conformance fixtures.
Integrations vendor this contract at a pinned version. **This repo vendors no integration's
contract.**

A **stand-in integration** with its own small schema and view, built only from the contract,
is the e2e stage's worker. So no gate depends on fate. Fate's own play is a recorded live run
against the hosted database.

## Still deferred

| Deferred | Why it waits |
|---|---|
| Moving books, chapters and blocks onto the generic core | Proves nothing v0.3 needs, and reworks the v0.2 that just shipped. Works are shaped so a book could become one, published by an external generator. Parked as its own decision |
| Code renderers per kind (`client/src/kinds/<kind>/`, a `schema_id → component` registry) | Each would put one integration's code in this repo. Waits until a view manifest provably cannot express a view that is needed |
| Several people sharing one branch (live multiplayer) | One owner per branch proves the tree. Shared turn order is a second permissions model |
| Comments, votes and merges on branches | Merging immutable storylines has no meaning yet; comments wait for a community |
| A cloud-hosted engine or model | The engine and its local LLM stay on the owner's PC. A request waits while it is offline |
| Windows-native dev scripts for this repo | The fate worker runs on Windows, but this repo's dev environment stays on its Linux host |
| Real integrations beyond fate | The contract and the stand-in are the proof. A second real integration is a later release's thesis |

## Definition of Done for v0.3

1. `./scripts/verify.sh` exits 0 from a clean clone.
2. No reducer can change or delete an existing node, and the gate turns red if one is added
   that does.
3. A non-owner client cannot read owner-only state, proved by a live-database test in the
   style of `answer-key.spec.ts`.
4. A signed-in viewer forks from a node in the middle of a branch. The new branch is private
   to them, the original is unchanged, and the side panels show each branch's own documents.
5. Over-cap fork requests are refused by a reducer, not by the client.
6. A seeded work plays one turn from the browser through a worker that knows only
   `docs/contracts/integration/`. In CI that worker is the stand-in. In a recorded live run it
   is `fate_core_llm`'s worker (its M94/M95), against the hosted database.
7. No code in `server/`, `client/` or `scripts/` names an integration or one of its
   concepts, and a verify stage fails if one does. Fate's panels render through the views it
   registered, with no commit to this repo.
8. CI is green on `main`.

Item 2 is the load-bearing one. A timeline that can be quietly edited is just a save file
that lies.

## Amendment 2026-11-19

The human's ruling: Book of Chaos stays agnostic to the kind of book and to the integration
that generates it. The approved text kept the server fate-blind, but it put fate in the
client: renderers in `client/src/kinds/fate/`, a vendored copy of fate's
`docs/contracts/boc/`, and a fate stand-in in CI. What changed:

- **The contract direction is inverted.** This repo owns `docs/contracts/integration/`, and
  integrations vendor it. Fate registers its schemas and views on its work as data.
- **Display is declarative.** `work_schemas` (M16) carries each schema's view manifest, and
  generic blocks draw it (M20). The `schema_id → component` registry is parked.
- **The composer belongs to the shell** (M20), because any interactive integration needs one.
- **CI's stand-in is a generic integration** (M21), so no gate depends on fate.
- **A guard stage** keeps integration names out of `server/`, `client/` and `scripts/` from
  M16 on.
- **v0.2 books stay on their own tables.** Moving them stays parked, as before.

### Amendment 2026-11-19, later the same day: anonymous readers

The human's ruling, made when enabling SpacetimeAuth (decision
[0002](./decisions/0002-durable-sign-in.md)): its **anonymous login stays on**, and an
anonymous reader gets **read-only access to the books enabled for anonymous access**. So:

- A book gains an owner-set "anonymous access" setting. An anonymous caller reads only the
  books that have it, and calls no writing reducer at all.
- "Anonymous" means any caller who is not durably signed in: SpacetimeDB's own anonymous
  tokens, an untrusted issuer, and SpacetimeAuth's anonymous login alike.
- Reads are enforced by the server, not hidden by the client. The book tables are public
  today, so this is decision [0001](./decisions/0001-owner-only-reads.md)'s pattern (private
  tables behind a caller-aware view) applied to books. That makes it the one exception to
  "v0.2 books stay unchanged" above. It lands in M15.3.
- **An anonymous reader can take quizzes, but the server saves nothing for them.** The
  answer key still never leaves the server, so grading still happens there. The anonymous
  path is a `#[procedure]` that reads the key and *returns* the verdict, and writes no
  `quiz_attempts` or `reader_progress` row. The reader's browser may keep their verdicts and
  progress in local storage. The UI says plainly that this can be lost, and that signing in
  keeps it. A signed-in reader's progress stays in the database, as in v0.2.
- That local progress drives unlocks for that one reader only, so it is a convenience, not a
  trust boundary. It gates nothing any other identity sees, and the books it unlocks are
  ones the reader could already read.
