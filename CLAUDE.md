# Book of Chaos — Working Agreement

Interactive knowledge publishing engine. Content is a **dependency graph**, not a page
sequence. Built on SpacetimeDB.

## Environment

The host is **Bazzite** (immutable Fedora Silverblue). It has no Rust, no Node, and no
SpacetimeDB, and it should stay that way. All build tools live in a `distrobox`
container whose home is `.devhome/` inside the repo.

```bash
./scripts/dev.sh setup           # one-time: build image, create container, install toolchains
./scripts/dev.sh run '<cmd>'     # run any command inside the container
./scripts/dev.sh doctor          # toolchain versions
./scripts/verify.sh              # THE quality gate — the only verdict that counts
```

Never `dnf install` or `rpm-ostree install` on the host. If a tool is missing, add it to
`Containerfile` or `scripts/install-toolchain.sh`.

## The verify gate

`./scripts/verify.sh` is the single source of truth for build health. CI runs it, the
Stop hook runs it, you run it. A task is not done until it exits 0.

Stages SKIP when their source directory does not exist yet — expected during early
milestones. A stage whose source exists but whose toolchain is missing is a FAIL. When
you add a new checkable surface, add its stage to `verify.sh` in the same commit.

## Layout

```
server/                 SpacetimeDB module (Rust → wasm32-unknown-unknown)
  src/unlock.rs         dependency/unlock engine — pure functions, no DB types
client/                 Vite + React + TypeScript reader/author UI
  src/module_bindings/  GENERATED by `spacetime generate` — never hand-edit
  src/i18n/en-US.ts     all user-facing strings
scripts/                dev container, verify gate, seed, deploy
docs/                   scope, backlog, escalations, runbook
```

## Conventions

**Rust / server**
- Reducers validate authorization first, then inputs, then mutate. No exceptions.
- Business logic lives in pure functions taking plain data; reducers are thin adapters.
  The unlock engine must be testable without a running database.
- Errors are `Result<(), String>` with messages written for a human reading a toast.
- Every reducer needs at least one happy-path test and one rejection test.

**TypeScript / client**
- `strict: true`. No `any`, no non-null `!` assertions on SDK results.
- No user-facing string literals in JSX — everything goes through `t()`.
- CSS uses logical properties (`margin-inline-start`, not `margin-left`).
- Server state is read from subscriptions, never refetched imperatively. If the UI needs
  a reload to be correct, it is wrong.

**Both**
- Trust boundary is the reducer. Client-side checks are UX, never security.
- Sanitize block HTML server-side, on write.

## Git

- Work on `main` for MVP velocity; the verify gate is the safety net.
- One task per commit. Message format: `M3.2: detect dependency cycles`.
- Tick the backlog checkbox in the same commit as the work it describes.
- Never commit `.devhome/`, `target/`, `node_modules/`, or identity tokens.

## Scope discipline

The design document is full of tempting features. Building any of them before v0.1 ships
is the primary risk to this project. When an idea arrives mid-task, append it to the
parking lot at the bottom of `docs/backlog.md` and carry on.
